# @composable/runes Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A thin rune-style layer, `component`, `state` and `event`, that produces ordinary core Components. After it, a measurement of the core's and the layer's performance and scalability.

**Architecture:** One file, `packages/runes/src/index.ts`.
- **Deep state:** a Proxy marks the instance dirty on every write.
- **Ops:** `component` runs `make` once at definition time to find the members and registers them as ops.
- **Instances:** each instance runs `make` again for its own state. A microtask flush re-reads the getters and publishes JSON copies of those that changed.

**Tech Stack:** Bun, TypeScript, TypeBox, `@composable/core`.

**Spec:** `docs/superpowers/specs/2026-11-09-runes-design.md`

## Global Constraints

- `packages/runes`, `@composable/runes`. Its dependencies are `@composable/core` (`workspace:*`) and `typebox` `^1.4.0`.
- `src/index.ts` is at most ~200 lines, aiming for 50–100. Each export has a 1–2 line purpose comment.
- The only core change is `Component<A = any>`, in `packages/core/src/component.ts`.
- Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. A subscriber mutating a value it received must not change the component's state. The copy is a JSON round trip (Task 2).
2. Several writes in one tick produce one publish per changed getter (Task 2).
3. A getter whose value is unchanged after a write is not published (Task 2).
4. `state()` or `event()` called outside `make` throws a clear error (Task 2).
5. The time a publish takes grows with the number of matching subscriptions. Measure `registry.matching`, a linear scan, against a growing number of subscriptions (Task 4).

### Task 2: `packages/runes`

**Produces:**
- `state<T extends object>(init: T): T`
- `event<S extends TSchema>(schema?: S): (data: Static<S>) => void`
- `component<A extends object>(id: string, make: () => A, schemas?: { [K in keyof A]?: TSchema }): Component<A> & { ops: { [K in keyof A]: Op } }`

**Tests** (`packages/runes/test/runes.test.ts`):
- The spike's counter, and slider → debounce (with a frequency slider) → table, wired and called through `X.ops.*` with no strings.
- A deep write `s.items.push(x)` publishes the getter.
- Three writes in one tick give one publish.
- A write that leaves a getter's value unchanged publishes nothing.
- A listener that mutates the array it received leaves the component's getter value unchanged.
- `event` publishes its argument, and calling it as an action gives `{ error }` (unknown op).
- `state()` outside `make` throws.
- No publish happens on creation.
- `snapshot()` lists the ops at `instance-added`.

- [ ] Write the tests. Run them and expect FAIL (module missing).
- [ ] Implement `src/index.ts` and `package.json`, then run `bun install`.
- [ ] Run `bun test`, tsc and `wc -l`. Expect PASS. Commit `feat(runes): component, state and event over core`.

### Task 4: Measure performance and scalability

Write `packages/runes/bench.ts`, run with `bun packages/runes/bench.ts`. It is not a test. It prints a table of operations per second, or µs per operation, for:
- a core `call` to one action;
- `notify` to 1, 10, 100 and 1000 subscribers;
- `notify` with 1 matching subscriber among 10, 1k and 10k non-matching subscriptions, the `matching` scan;
- `registry.add` of 10k instances;
- a runes write followed by a flush, with 1, 10 and 100 getters and with state of 10 and 1000 array items.

- [ ] Write it and run it. Record the numbers in the commit message and the final report, with what scales linearly and where the first fix would go.
- [ ] Commit `chore(runes): performance and scalability bench`.
